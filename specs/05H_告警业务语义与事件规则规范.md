# 05H_告警业务语义与事件规则规范

## 适用范围

本规范定义项目五中“检测结果、候选事件、告警、告警解释”的业务语义边界。所有 Jetson 和 RK3588 run 必须引用本规范；RDK X5 因项目四准入失败，已从项目五主线实验中移除。

项目五第一阶段不是通用安防语义识别系统，也不只是“画面里有人/车”的分类器。它是基于项目三 YOLO11n 检测结果和项目四 LLM/VLM 准入结果，生成可追溯、可解释、可结构化、可 benchmark 的边缘告警解释系统。没有检测类别、区域规则、跟踪证据或人工标签支撑的告警类型，不能写成已实现能力。

## 系统任务定义

项目五告警解释系统的核心任务是：把实时目标检测结果转化为带证据、带解释、带结构化字段和带性能记录的边缘告警输出。

系统的业务处理对象不是原始视频本身，而是“检测事实、视觉证据、运行日志、模型输出和 JSON 质量记录”共同组成的告警证据链。LLM/VLM 的职责是解释和复核证据，不是替代 detector 产生事实。

标准任务链路：

```text
YOLO detection facts
-> candidate event package
-> keyframe / ROI / clip evidence
-> LLM text explanation
-> optional low-frequency VLM ROI review
-> alarm JSON
-> benchmark and stability evidence
```

项目四的 `B_low_frequency` 是项目五可接入路线边界，不是项目五真实运行证据。Jetson/RK3588 报告必须同时给出项目五 event package、真实模型 raw、runtime log、monitor log 和 `model_execution` 状态；只有 route stub、template LLM 或缺失 ROI/keyframe 资产时，不能写成真实 LLM/VLM 告警解释能力。

项目五任务域统一用 `alarm_domain` 表达，具体告警或解释任务用 `alarm_type` 表达。当前必须区分下面几类任务：

| alarm_domain | 系统任务 | 主要输入 | 主要输出 | 项目四依据 |
|---|---|---|---|---|
| `visual_detection` | 从项目三检测结果生成候选视觉告警事件 | frame-level detection JSONL | event package、候选风险说明、alarm JSON | 项目三检测 pipeline；项目四 `text_detection_json_001`、`text_alarm_reason_001` |
| `visual_evidence` | 对关键帧、ROI、面板/异常图片做低频视觉复核 | keyframe、ROI、固定图片证据 | `vlm_summary`、证据描述、fallback | 项目四 image/ROI VLM 固定输入 |
| `text_explanation` | 对检测 JSON、候选事件和告警原因做文本解释 | detection JSON、event package、prompt | `llm_explanation`、risk/action、schema-safe JSON | 项目四 text LLM 固定输入 |
| `system_runtime` | 对视频源、检测 pipeline、队列和服务故障做运行解释 | runtime log、queue metrics、failure log | runtime fault alarm、fallback 状态 | 项目四 `text_log_001` |
| `model_runtime` | 对 LLM/VLM timeout、OOM、unsupported runtime 做模型故障解释 | model log、timeout/OOM 记录 | model fault alarm、禁用/降级原因 | 项目四失败和 fallback 报告 |
| `json_quality` | 对 JSON 非法、事实冲突和 schema 修复做质量记录 | LLM/VLM raw、alarm JSON、schema check | `json_fact_conflict`、repair/fallback | 项目四 `text_json_output_001` |
| `video_fallback` | 记录视频理解禁用后的替代摘要策略 | clip path、keyframe、detections | detector/keyframe/ROI derived `video_summary` | 项目四 SmolVLM2 `D_not_used` |

因此，人、车、多目标只是 `visual_detection` 域里的第一阶段候选事件；项目五完整系统还必须覆盖文本解释、视觉证据复核、模型/系统失败降级和 JSON 质量闭环。

## 项目四任务到项目五任务映射

| 项目四输入任务 | 项目五对应任务 | alarm_domain | alarm_type | 项目五使用方式 |
|---|---|---|---|---|
| `text_log_001` | 设备/服务日志解释 | `system_runtime` | `pipeline_runtime_fault` | 解释断流、队列堆积、服务异常和恢复动作 |
| `text_deploy_error_001` | 模型部署错误解释 | `model_runtime` | `model_runtime_fault` | 解释 runtime 不支持、模型加载失败、timeout/OOM |
| `text_detection_json_001` | 检测 JSON 摘要 | `text_explanation` | `detection_json_summary` | 将检测事实转成操作员可读摘要，不改写类别/框 |
| `text_alarm_reason_001` | 告警原因、风险和动作建议 | `text_explanation` | `alarm_reasoning` | 输出风险等级和 recommended_action |
| `text_json_output_001` | schema-safe JSON 生成 | `json_quality` | `alarm_json_generation` | 约束告警 JSON 字段完整性和修复策略 |
| `image_yolo_bus_001` | 交通/街景视觉证据复核 | `visual_evidence` | `visual_abnormal_review` | 低频关键帧/ROI 复核，不替代 detector |
| `image_workstation_001` | 工作区场景复核 | `visual_evidence` | `visual_abnormal_review` | 描述可见异常、目标和场景状态 |
| `image_panel_001` | 设备面板/指示灯状态复核 | `visual_evidence` | `device_panel_state_review` | 只描述可见状态，不推断不可见故障 |
| `image_roi_object_001` | ROI 目标复核 | `visual_evidence` | `roi_object_review` | 对候选事件的 ROI 做补充描述 |
| `image_abnormal_001` | 可见异常现象描述 | `visual_evidence` | `visual_abnormal_review` | 作为低频 VLM 解释任务 |
| `video_*` | 短片段视频理解 | `video_fallback` | `video_summary_disabled` | 当前 Jetson/RK3588 项目五主线不接入 SmolVLM2 视频模型，使用检测/抽帧/ROI/text 摘要替代 |

## 第一阶段主要功能

| 功能 | 作用 | 当前边界 |
|---|---|---|
| 候选告警生成 | 从检测帧中筛选人员、车辆、多目标场景事件 | 只能生成 `candidate`，不能直接写 `verified` |
| 告警解释 | 用 LLM 解释触发原因、目标位置、置信度和建议动作 | LLM 不得改写检测类别、框和置信度 |
| ROI/关键帧复核 | 低频调用 VLM 对关键视觉证据做补充描述 | Jetson/RK3588 均为 `B_low_frequency`，只能低频异步 |
| 结构化输出 | 生成可被下游系统消费的 alarm JSON | schema pass 只代表格式合格，不代表业务质量 pass |
| 证据追溯 | 通过 event_id 追溯 frame、detections、ROI、模型输出和日志 | 缺任一核心证据时状态必须降级 |
| Benchmark | 统计每类候选事件数量、延迟、资源、fallback 和稳定性 | 缺人工标签时不能计算误报率/召回率 |

## 非目标

第一阶段明确不做下面事情：

| 非目标 | 原因 |
|---|---|
| 直接识别人员入侵/越界 | 需要 zone 和进入判定 |
| 识别徘徊/滞留 | 需要 tracking_id 和持续时间 |
| 识别跌倒/打架/奔跑等动作 | YOLO11n COCO 检测类别不支持 |
| 识别烟火 | 当前检测模型不支持烟火类别 |
| 用 LLM 判断检测是否真实存在 | LLM/VLM 只能解释和复核，不能覆盖检测事实 |
| 用 schema pass 证明业务质量 pass | schema 只验证字段，不验证告警正确性 |

## 开源系统参考

成熟开源视频告警系统普遍采用“检测事实 -> 事件/告警分类 -> 截图/片段证据 -> 通知/解释”的分层模型，项目五按这个口径收敛：

| 系统 | 可参考设计 | 项目五采纳方式 |
|---|---|---|
| Frigate | 本地实时目标检测、按 zones/labels 区分 detections 和 alerts、event_id 可取 snapshot/clip、GenAI 可对 review item 生成结构化摘要 | 区分 `candidate_event` 和 `alarm_json`；规则必须包含类别、阈值、持续帧、冷却和可选 zone；LLM/VLM 只解释事件证据 |
| ZoneMinder | Monitor、Events、Zones 分层；通过 zone 排除不关心区域，降低误触发 | 项目五必须记录 source/camera、zone、trigger_rule_id 和 ignored 区域 |
| Shinobi | Detection and Events、Object Detection、Event Filters、Alarms 分层，支持 detector plugin 和 event filtering | 事件触发规则必须独立于检测服务；告警输出必须保留过滤规则和 detector 原始事实 |
| OpenVINO demos | 多模型流水线示例强调预处理、后处理和多模型分析数据汇聚 | 项目五 benchmark 必须拆检测、事件、ROI、LLM/VLM、JSON 和资源指标 |

## 术语分层

| 术语 | 定义 | 是否等同业务告警 |
|---|---|---|
| detection | 项目三 YOLO 输出的一帧检测事实，包含 class、confidence、bbox | 否 |
| candidate_event | 项目五事件规则从 detection 派生的候选事件包 | 否 |
| verified_alarm | 满足业务规则、证据资产、LLM/VLM 输出和 schema 的告警 | 是，但需质量评估 |
| alarm_json | 结构化告警输出格式，可能承载 candidate 或 verified 状态 | 不一定 |
| explanation | LLM/VLM 对检测事实、ROI、关键帧和规则的解释 | 不是事实来源 |

LLM/VLM 输出只能补充解释，不能覆盖 detector 原始事实。没有人工标签或固定事件集质量评估时，系统状态只能写 `not_verified`，不能写 `pass`。

## 第一阶段候选视觉告警类型

第一阶段仅实现项目三 YOLO11n COCO 类别能够支撑的 `visual_detection` 候选告警。正式报告必须使用 `candidate` 或 `not_verified` 状态，除非后续补充固定事件集和人工质量评估。

| alarm_domain | alarm_type | trigger_rule_id | 触发类别 | 最低证据 | LLM/VLM 解释目标 | 质量状态 |
|---|---|---|---|---|---|---|
| `visual_detection` | `person_presence` | `person_presence_candidate` | `person` | 连续帧中存在人员检测框、置信度达标、event_id 可追溯 | 解释人员数量、位置、置信度、是否进入指定 zone | `candidate/not_verified` |
| `visual_detection` | `vehicle_presence` | `vehicle_presence_candidate` | `car`、`bus`、`truck`、`motorcycle`、`bicycle` | 连续帧中存在车辆类检测框、置信度达标、event_id 可追溯 | 解释车辆类型、数量、位置和是否进入指定 zone | `candidate/not_verified` |
| `visual_detection` | `multi_object_scene` | `multi_object_scene_candidate` | person/vehicle 多目标 | 同一触发帧达到最小目标数，且类别属于规则白名单 | 总结场景中主要目标和潜在注意点 | `candidate/not_verified` |

## 告警解释任务类型

下面类型不是直接由检测框触发的业务告警，而是告警解释系统必须能表达和记录的解释任务、复核任务或降级任务：

| alarm_domain | alarm_type | 触发来源 | 输出要求 | 状态边界 |
|---|---|---|---|---|
| `visual_evidence` | `roi_object_review` | ROI/keyframe 低频 VLM 调用 | `vlm_summary` 描述 ROI 可见目标、位置和不确定性 | 不得覆盖 detector 类别 |
| `visual_evidence` | `visual_abnormal_review` | 异常图片、工作区或关键帧复核 | 描述可见异常现象和证据限制 | 无人工标签时 `not_verified` |
| `visual_evidence` | `device_panel_state_review` | 面板/设备图片 | 描述指示灯、屏幕、开关等可见状态 | 不推断不可见电气故障 |
| `text_explanation` | `detection_json_summary` | detection/event JSON | 面向操作员的检测事实摘要 | 必须保留原始事实 |
| `text_explanation` | `alarm_reasoning` | event package + rule | 告警原因、风险等级、建议动作 | 不能把 candidate 写成 verified |
| `json_quality` | `alarm_json_generation` | LLM 输出和 schema | schema-safe alarm JSON | schema pass 不等于业务 pass |
| `system_runtime` | `pipeline_runtime_fault` | runtime/failure log | 断流、队列、服务状态解释和恢复建议 | 必须进入问题库或 fallback |
| `model_runtime` | `model_runtime_fault` | LLM/VLM runtime log | timeout、OOM、runtime unsupported、禁用原因 | 不得继续声明模型可用 |
| `json_quality` | `json_fact_conflict` | schema/fact conflict check | `json_fact_conflict=true` 和冲突详情 | 需要修复或人工复核 |
| `video_fallback` | `video_summary_disabled` | 项目四视频模型 `D_not_used` | `fallback_status.video=disabled_by_project4_decision` | 不得声称视频模型理解已运行 |

下面类型当前不得写成已实现能力：

| 禁用告警类型 | 禁用原因 | 后续启用条件 |
|---|---|---|
| `person_intrusion` | 需要明确 zone 和进入/离开判定；当前 smoke 未配置真实 zone | 为输入源配置 zone，多帧跟踪或 bottom-center 判定通过 |
| `person_loitering` | 需要跟踪 ID 和停留时长 | 引入 tracking_id 和持续时间统计 |
| `crowd_gathering` | 需要人数阈值、场景区域和误报评估 | 固定事件集人工标注并完成质量评估 |
| `fall_detection` | YOLO11n COCO 不支持跌倒语义 | 增加姿态/动作模型或人工标注验证 |
| `fire_smoke` | YOLO11n COCO 不支持烟火类别 | 增加烟火模型并完成项目一/三/四准入 |
| `restricted_object` | 需要业务禁区和目标类型定义 | 配置 zone、对象白名单/黑名单和人工验收集 |

## 事件规则要求

事件规则必须至少包含：

| 字段 | 要求 |
|---|---|
| `rule_id` | 全局唯一，必须体现业务语义，不允许正式 run 使用 `generic_object_event` |
| `alarm_domain` | 必须属于本规范定义的任务域；检测触发规则默认 `visual_detection` |
| `alarm_type` | 必须属于本规范定义的候选视觉告警类型、解释任务类型或降级任务类型；新增类型必须在 run 记录中标明 `experimental` 并更新 schema |
| `class_filter` | 不允许正式 run 为空；为空只能用于接口调试 |
| `confidence_threshold` | 每类规则独立设置，默认不低于 `0.60` |
| `duration_frames` | 连续满足帧数，默认不低于 `3` |
| `cooldown_seconds` | 同一规则冷却时间，默认不低于 `10` |
| `min_object_count` | 多目标规则必须大于等于 `2` |
| `zone` | 可选；没有 zone 时不得写入 intrusion/越界结论 |
| `snapshot_policy` | 默认 `best_confidence` |
| `clip_policy` | 默认 `pre_post` |

## 输出语义要求

event package 应额外写入：

```text
alarm_domain
alarm_type
event_stage=candidate | verified | rejected
trigger_rule_id
trigger_reason
```

alarm JSON 应区分：

```text
alarm_domain
alarm_type
event_stage
alarm_status=candidate | verified | fallback | rejected
explanation_status=real_model | template_fallback | not_executed
fact_conflict=true | false
```

如果只有 schema pass，没有真实 ROI/keyframe、真实 LLM/VLM 或人工质量评估，则报告状态必须是 `not_verified_interface_smoke` 或 `not_verified_candidate_only`。

## Benchmark 要求

除原有 latency、资源和 schema 指标外，报告必须按 `alarm_domain` 和 `alarm_type` 聚合：

| 指标 | 说明 |
|---|---|
| candidate_event_count_by_domain | 每个任务域的候选事件或解释任务数量 |
| candidate_event_count | 每类候选事件数量 |
| event_rate_per_min | 每分钟候选事件数，用于判断规则是否过宽 |
| duplicate_suppression_count | 冷却、持续帧、队列策略抑制的重复事件数 |
| candidate_to_verified_rate | 有人工验证或固定事件集时才可填写 |
| false_positive_rate | 需要人工标签，缺失时必须写 `not_available` |
| explanation_coverage | 有多少候选事件获得真实 LLM/VLM 解释 |
| fallback_count_by_domain | 系统、模型、视频和 JSON 降级次数 |

## 验收标准

- Jetson 和 RK3588 的正式 run 不再使用 `generic_object_event`。
- RDK X5 不进入项目五主线实验、benchmark 横向比较和稳定性验收。
- 所有候选事件都能追溯到 detection、frame_id、rule_id、alarm_domain、alarm_type、ROI/keyframe/clip 路径和模型输出。
- 没有 zone/tracking/人工标签时，不得声称完成越界、徘徊、聚集、跌倒、烟火等业务告警。
