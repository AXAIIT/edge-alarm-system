# 05K_常驻服务与并发验收规范

## 目的

本规范定义项目五最终要交付的系统形态。项目五的目标不是只证明脚本能串起来，也不是只证明 LLM/VLM 单次可运行，而是在边缘开发板上形成一个可持续运行的告警解释服务：

```text
常驻检测服务
-> 有界事件队列
-> 低频异步 LLM/VLM worker
-> 持续输出 schema-safe Alarm JSON
-> 记录 benchmark、资源、fallback 和故障恢复
```

因此，`run_demo` 脚本、raw replay、single-shot LLM/VLM 和手工串联命令只能作为模块证据或接口 smoke。最终系统验收必须证明检测服务、事件队列、解释 worker 和告警输出在同一持续运行窗口内协同工作，并且 LLM/VLM 不阻塞检测。

这里的“模型一次加载、常驻”定义为：模型在其 worker 进程启动时初始化，在该进程处理多个事件期间不重复完整加载；只有进程被显式停止、异常退出或受控重启后才允许重新加载。它不是指系统永不重启。最终证据必须记录每个 worker 的 `model_load_count`、`restart_count`、冷启动耗时和 warm 请求时延；任何“每个事件重新启动 runner 并加载模型”的实现都不得声明 resident LLM/VLM。

常驻服务验收还必须满足 `projects/05_alarm_system/specs/05L_项目五独立代码库与适配边界规范.md`。最终 service 入口、队列、worker、AlarmSink 和运行编排必须在 `projects/05_alarm_system/` 内实现；直接执行项目三或项目四脚本只能作为 legacy smoke，不能支持 `resident_service_required`。

从当前模块证据走向最终系统的阶段顺序、每阶段的实现任务、产物和声明边界，以 `projects/05_alarm_system/specs/05M_常驻告警系统实施路线图.md` 为准。本规范定义验收契约，不允许跳过路线图中的 detector、资产和 resident worker 阶段。

## 系统边界

| 模块 | 是否必须常驻 | 频率要求 | 最低实现 | 最终验收要求 |
|---|---|---|---|---|
| `DetectorService` | 必须 | 高频，接近项目三基线 FPS | 继承项目三 C++ pipeline，持续写 frame-level detection raw 或事件流 | 30 分钟 required 内持续运行，FPS/p95/drop 可解释 |
| `EventTrigger` | 必须 | 随检测帧持续执行或批量低延迟执行 | 根据 detector raw/stream 生成 event package | 记录 trigger latency、冷却、持续帧、重复抑制 |
| `EventQueue` | 必须 | 有界异步 | `event_queue_max`、drop policy、queue depth 字段齐全 | 队列满时不阻塞检测，drop_count/drop_reason 可追溯 |
| `AssetWorker` | 应常驻或按事件快速启动 | 仅事件触发 | 生成 keyframe/ROI/clip 路径 | ROI/keyframe 资产可读，失败可 fallback |
| `TextWorker` | 最终验收必须常驻或 warm pool；single-shot 只能算 smoke | 低频异步 | 事件触发调用 Qwen3 文本 LLM 或模板 fallback | timeout 不阻塞检测，输出按 event_id 对齐；真实模式有 load/warm 证据 |
| `VlmWorker` | 最终验收必须常驻或 warm pool；single-shot 只能算 smoke | 低频异步，不逐帧 | 只处理关键帧/ROI | timeout 不阻塞检测，不能覆盖 detector 事实；vision/decoder 有 load/warm 证据 |
| `AlarmJsonBuilder` | 必须 | 随事件持续输出 | schema-safe Alarm JSON | JSON schema pass，fact conflict 可记录 |
| `Monitor` | 必须 | 1s 或可解释采样间隔 | 复用板卡原生 monitor | 资源、温度、swap、service status、错误和重启可追溯 |

`alarm_system_stability.jsonl` 的 `window_sec` 必须是 service 的实际墙钟运行时长，不能填目标值。若设置了目标窗口，必须同时写 `requested_window_sec` 与 `window_requirement_met`；`resident_process` 实际时长短于目标时，service 必须写 `status=fail`、`service_status=failed` 并以非零退出。`window_sec=600` 不是 10 分钟证据，只有 `requested_window_sec=600`、`window_sec>=600`、`window_requirement_met=true` 和 monitor 覆盖窗口同时成立才是。

## 能力声明等级

| 等级 | 可声明内容 | 不可声明内容 | 必需证据 |
|---|---|---|---|
| `interface_smoke` | 字段、schema、路径和脚本接口可用 | 真实模型能力、稳定性、并发 | event/alarm/per-event schema pass |
| `single_shot_model_smoke` | 某个真实 LLM/VLM 能对项目五事件输入输出结果 | resident model、持续服务、并发稳定性 | model raw/log/metrics，event_id 对齐 |
| `post_detector_chain_pass` | detector 已完成实时 run，项目五后处理链路可闭环 | 同一服务内并发隔离 | Project3 realtime raw + Project5 event/alarm/per-event raw |
| `resident_service_smoke` | 常驻检测 + 异步解释服务可持续 10 分钟 | 30 分钟 required 或生产化稳定 | service log、queue metrics、monitor、schema pass |
| `resident_service_required` | 常驻服务满足 30 分钟最低验收 | 2 小时目标或生产级稳定 | time-window raw、per-event raw、monitor、error/restart/drop |
| `resident_service_target` | 常驻服务满足 2 小时目标 | 8 小时压力或生产级 SLA | 2h sustained raw、资源曲线、异常注入 |

`resident_service_required` 还必须同时满足 `code_boundary_status=independent_runtime_pass`。如果检测、LLM 或 VLM worker 仍直接依赖 `projects/03_video_pipeline` 或 `projects/04_llm_vlm_independent` 下的脚本，等级必须降为 `legacy_adapter_smoke` 或 `post_detector_chain_pass`。

双板联调是额外的组级声明，不替代单板等级。当前双板组级口径定义为：

| 组级等级 | 可声明内容 | 最低条件 |
|---|---|---|
| `dual_board_required_ready` | Jetson accepted 路线与 RK3588 accepted 路线在同一联调批次内同时满足 `required` | 两板各自 `resident_service_required` 成立，启动偏差 `<=300s`，有效窗口重叠 `>=1500s` |
| `dual_board_target_ready` | Jetson accepted 路线与 RK3588 accepted 路线在同一联调批次内同时满足 `target` | 两板各自 `resident_service_target` 成立，启动偏差 `<=300s`，有效窗口重叠 `>=6900s` |

双板执行顺序、命名和组级记录格式以 `projects/05_alarm_system/specs/05N_双板联调执行流程.md` 为准。

报告中不得把低等级证据写成高等级结论。例如：

- `rkllm_multimodal_once` 只能支持 `single_shot_model_smoke`，不能支持 `resident_service_required`。
- Project3 detector 30 分钟加 Project5 后处理可以支持 `post_detector_chain_pass`，不能自动支持 `resident_service_required`。
- VLM route stub 只能支持 `interface_smoke`，不能支持真实 VLM 能力。

当前可执行的 template/stub smoke 的运行生命周期如下：

```text
run_alarm_service.py
  -> ResidentProcessDetectorService 以 Popen 启动一次 Project5 detector binary
      -> detector 启动时按 inference_workers 初始化 RKNN/TensorRT backend 并 warmup
      -> 持续读取视频/摄像头，追加 frame-level detector JSONL
  -> Project5 service tail JSONL，按规则生成 event package
  -> BoundedEventQueue.put_nowait
  -> 独立 alarm-worker 线程消费事件
      -> template TextWorker（不加载真实 LLM）
      -> stub VlmWorker（不加载真实 VLM）
      -> AlarmJsonBuilder + JSONL writers
  -> detector 正常退出或服务停止后，关闭队列、等待 worker、关闭 writer 和 monitor
```

`inference_workers=3` 时，detector 会创建 3 个常驻 RKNN backend/context；每个 context 在 detector 进程启动时各加载一次并在整个运行窗口内复用。这是并行检测配置，不是每帧或每事件冷启动。template/stub smoke 中 `llm_call_count=0`、`vlm_call_count=0` 是“未加载真实解释模型”的必要证据，而不是模型常驻证据。

| 层级 | 当前 Project5 实现 | 采用的稳定性技术 | 已知边界 |
|---|---|---|---|
| detector 生命周期 | `ResidentProcessDetectorService` 以子进程启动 Project5 本地 runner，等待 JSONL 创建后 tail | 启动超时、子进程非零退出失败、窗口结束时 `terminate`，5 秒后强制 `kill` | 当前没有自动重启策略；异常退出会使本次 run 失败并保留日志 |
| detector 数据流 | C++ detector 仅在启动时初始化 backend 和 warmup，之后持续追加 JSONL | frame-level JSONL 追加写入、service 每 0.2 秒轮询读取新增行、非法 JSON 立即失败 | 需要 RK3588 板端 10 分钟 run 证明真实 runner 的持续输出 |
| 规则与抑制 | `DetectorRuleEngine` 对 person、vehicle、multi-object 等规则维护连续帧与冷却状态 | `duration_frames`、按规则 `cooldown_seconds`、`min_frame_gap`，减少重复告警和队列冲击 | 不等同于事件质量标注集验证 |
| 背压隔离 | `BoundedEventQueue` 将 detector 产出的事件交给独立 alarm worker | `Queue.put_nowait`、固定 capacity、`drop_newest`、max-depth 和 drop_count 统计；队列满时不等待 worker | 当前只有一个 alarm worker，真实 LLM/VLM 很慢时会造成事件降级，后续需限流/优先级策略 |
| template/stub | 独立 worker 线程生成确定性 fallback | 不调用 `llama-cli`、RKLLM 或 Qwen3-VL runner，避免测试中发生模型冷启动 | 只能验证 detector、队列、AlarmSink；不能证明真实解释能力 |
| 产物与监控 | 持续写 event、LLM、VLM、Alarm JSON、per-event raw、time-window raw 和 service log | 4 类 JSON schema 校验；RK3588 monitor 每秒记录内存、温度、NPU 与进程信息 | schema pass 不自动代表吞吐、模型常驻或告警质量通过 |
| 独立代码边界 | service 拒绝把 Project3/4 路径作为 `--detector-command`；detector source/build/runner 位于 Project5 | Project5 code-boundary scan；前序项目只允许作为模型 artifact 或历史 evidence | resident adapter 已进入 Project5 本地代码边界；最终验收仍取决于板端 smoke/required 证据，而不是仅靠代码存在 |

当前 `run_alarm_service.py` 的 alarm worker 虽与 detector 生产线程解耦，但真实 `rkllm` 与 `rkllm_multimodal` worker 仍会对每个事件启动一次 runner；它们只能标为 `single_shot_model_smoke`。下一阶段必须在 Project5 内将二者替换为长生命周期 IPC worker：启动阶段加载模型一次，请求阶段仅传入 `event_id`、prompt 和 ROI/keyframe 路径，响应阶段返回对应 JSON。worker timeout、队列满、模型异常只能导致该事件 fallback，不能停止 detector。

## 2026-07-14 Jetson 收口策略

Jetson 当前不再把“detector resident + text resident + VLM resident 同窗”当作唯一默认主线，而是明确拆成两条可验收路线：

| 路线 | 组合 | 目标 | 当前判定意义 |
|---|---|---|---|
| Route A | `detector resident + VLM resident + text template` | 在 live detector 压力下单独验证 multimodal request path 和资产路径 | 用来回答“Jetson 的 resident VLM 在有 detector 时到底能不能稳定处理真实图片请求” |
| Route B realtime | `detector resident + text resident + VLM stub` | 把实时告警链路收敛到 detector + text，不让 VLM 进入主链路 | 用来回答“Jetson 的实时主链路是否已经具备可持续运行的 resident text 能力” |
| Route B async enrichment | `events_input + resident VLM` | 复用 Route B 的事件和媒体源，单独做低频视觉补充 | 用来回答“Jetson 的 VLM 是否适合作为异步 enrichment，而不是强行塞进实时链路” |

这样拆分不是权宜之计，而是基于当前 Project5 service 的真实实现边界：`run_alarm_service.py` 目前仍由单个 `alarm-worker` 顺序执行 `asset -> text -> vlm -> alarm`。因此“VLM 低频异步 enrichment”在当前版本中，正确的工程实现不是把 VLM 强塞回同一实时进程，而是启动独立的 Project5 异步 worker。当前仓库已补入 `run_async_vlm_enrichment.py` 和 `run_jetson_p7_route_b_dual_service_smoke.sh`：前者 tail 持久化的 `events.jsonl`、按 `event_id` 低频执行真实 VLM，并重建 enriched alarm snapshot；后者则在同一个 `RUN_ID` 下同时运行 realtime `detector + resident text` 与异步 VLM 进程。

### Route A 与 Route B 的声明边界

| 路线 | 通过后可声明 | 不能声明 |
|---|---|---|
| Route A | Jetson live detector 下 resident VLM request path、资产回填路径、同 pid / `model_load_count=1` 复用成立 | Jetson 实时文本主链路已完成 |
| Route B realtime | Jetson `detector + resident text` 实时链路成立，且 VLM 已被移出主路径 | Jetson resident VLM 可在同窗实时链路内稳定通过 |
| Route B async enrichment | Jetson resident VLM 适合作为低频异步 enrichment | Jetson 已完成同窗三常驻 `resident_service_required` |

### 为什么当前不建议继续把 Jetson 默认主线压在三常驻同窗上

1. Jetson 已经拿到 `resident_text_worker_smoke_pass` 和 standalone `resident_vlm_worker_smoke_pass`，说明问题已经不在“模型能不能单独常驻”。
2. `20260715_..._postrun_v1` 已经证明 Jetson 的“系统内低频 VLM 补充”能力是可成立的，剩余失败只属于 `parallel` 同窗干扰。
3. 因此更高价值的正式验收路线不再是继续无差别复跑旧 P7/P8 三常驻同窗，而是沿 `detector + resident text realtime + postrun async VLM` 推进 Jetson required；这条路线现在已经完成 Jetson 单板 required 验证。

这也是当前 Jetson 规范、wrapper 和报告必须同步改口的原因。

## 最小常驻服务验收

10 分钟 smoke 必须满足：

| 项 | 最低要求 |
|---|---|
| 检测 | detector 进程持续运行，输出帧级检测或事件流 |
| 队列 | event queue depth、drop_count、drop_policy 有记录 |
| 文本解释 | 至少一种文本路径启用：真实 LLM 低频调用或明确 template fallback |
| VLM | 可禁用、route stub 或真实低频；状态必须写入 fallback/status |
| Alarm JSON | 至少 1 条或明确 no-event；schema pass |
| 监控 | monitor log 覆盖运行窗口 |
| 错误 | error_count、restart_count、reconnect_count 明确 |
| 结论 | 只能写 `resident_service_smoke`，不能写 required |

30 分钟 required 必须额外满足：

| 项 | 最低要求 |
|---|---|
| 检测隔离 | LLM/VLM 调用期间 detector FPS、p95、drop rate 与项目三基线差异可解释 |
| 队列安全 | queue_depth 不持续增长；队列满时按策略丢弃或降级 |
| 模型超时 | LLM/VLM timeout 不导致 detector 停止或 Alarm JSON 中断 |
| 资源安全 | memory、swap、temperature、电源模式或功耗有记录 |
| schema | event package、Alarm JSON、per-event raw、time-window raw 均 pass |
| 状态 | 满足后才能写 `resident_service_required` |

2 小时 target 用于作品集增强，不能替代 30 分钟 required。

## 推荐服务架构

```text
DetectorService
  writes detections/events
EventQueue(max=N, drop_policy=drop_low_priority_or_duplicate)
  -> AssetWorker(keyframe/ROI/clip)
  -> TextWorker(rate_limit, timeout, fallback)
  -> VlmWorker(rate_limit, timeout, fallback)
AlarmJsonBuilder
  -> AlarmSink(JSONL/file/http)
BenchmarkRecorder
Monitor
```

`resident_process` 是当前唯一允许进入 B 方案常驻检测验收的 detector 输入模式。它要求：

- `--detector-command` 指向 Project5 本地 detector binary/wrapper。
- `--detector-output` 是该 detector 持续写入的 frame-level detection JSONL。
- service 对 detector 进程负责启动、等待输出、tail、窗口结束停止和异常返回码检查。
- service 会拒绝指向前序项目脚本路径的 detector command。

当前 PC 入口层 smoke 已验证 `20260709_pc_alarm_service_resident_process_smoke_v3`：Project5 本地 fake detector 由 service 启动，输出 events=3、alarms=3、per-event raw=3、stability raw=1，四类 schema 均 pass，`code_boundary_status=independent_runtime_pass`。该 run 只证明 resident-process 入口和队列/AlarmSink 机制，不替代 Jetson/RK3588 真实 detector binary 30 分钟 required。

## RK3588 常驻 VLM 特别要求

当前 `run_rkllm_multimodal_once.sh` 每次调用都会启动 runner 并加载模型，因此只能算 single-shot。若要声明 resident VLM，必须满足至少一个条件：

- 提供常驻进程，启动时加载 Qwen3-VL `.rknn` vision 和 `.rkllm` decoder，一次加载后处理多个 ROI 请求。
- 或提供可解释的 warm pool，证明多次事件请求没有重复完整 cold load，且资源稳定。

如果仍使用 `rkllm_multimodal_once`，报告必须写：

```text
vlm_execution=single_shot
resident_vlm=false
service_claim=not_verified
```

Project5 当前 resident VLM 路径已经补齐到本地代码边界：

- `projects/05_alarm_system/src/vlm_client/rkllm_resident_vlm_server.cpp`
- `projects/05_alarm_system/scripts/service/rkllm_resident_vlm_client.py`
- `projects/05_alarm_system/scripts/build/build_rk3588_rkllm_vlm_runners.sh`
- `projects/05_alarm_system/scripts/service/run_rk3588_vlm_resident_smoke.sh`
- `run_alarm_service.py --vlm-mode rkllm_multimodal_resident`

这意味着历史阻塞点已从“没有 resident VLM 代码”收敛并解除：RK3588 单板 P7/P8/P9、Jetson P4/P6-text/P6-VLM standalone、Jetson accepted Route-B P7/P8/P9、双板 target 和 Jetson publishable-text fact guard 均已完成。Jetson same-window resident VLM request path 仍可作为诊断问题保留，但不再阻塞 accepted Route-B 验收。

同时需要记录一个实现修正：在补 resident VLM 时，Project5 已修正 `run_vlm_roi_qa.py` 的 prompt 构造和默认多模态 token 配置，新的默认值会显式注入 `<image>`，并使用 Qwen3-VL 路线需要的 `<|vision_start|>` / `<|vision_end|>` / `<|image_pad|>` / `template_style=qwen`。因此历史 Project5 single-shot VLM service run 在未按新代码重跑前，应保守写成 `single_shot_route_smoke`，不要把它升级成 resident/warm 证据。

## Jetson 常驻 LLM/VLM 特别要求

Jetson 的 llama.cpp 路线如果使用交互会话或 server 模式，可以作为 resident/warm worker 候选；如果每个事件都重新启动 `llama-cli` 并加载模型，只能算 single-shot。使用 `script` 捕获交互输出时，必须保存 session log，并证明事件之间状态不会污染下一次告警。

截至当前源码与最新板端结果，Project5 Jetson 侧 `llama_cpp_resident` 模式已经拿到第一条正式复用证据：service 在启动时拉起本地 `llama-server`，随后用 HTTP 复用同一进程处理多个事件请求；`20260713_jetson_8gb_alarm_service_resident_text_smoke_v1` 已记录 `resident_server_pid=3828920`、`resident_model_load_count=1` 和请求序号 `1/2/3`，可声明 `resident_text_worker_smoke_pass`。Jetson resident VLM worker 模式也已实现为 `llama_cpp_multimodal_resident`，并配套 `run_jetson_p6_resident_vlm_smoke.sh`；最新 `20260713_jetson_8gb_alarm_service_resident_vlm_smoke_v4` 已证明 standalone multimodal `llama-server` 可以复用同一 `resident_server_pid=4611`、`resident_model_load_count=1` 处理 3 个事件请求，`vlm_bad_rows=0`。随后 `20260713_jetson_8gb_alarm_service_resident_concurrency_smoke_v8` 又进一步证明 Jetson P7 已进入 `window_requirement_met=true` 的有效 10 分钟窗口，且 `drop_count=0`；因此 Jetson 当前不能再写成“P6-VLM 没通过”或“P7 还没进有效窗”，而应准确写成“并发窗口中的 resident VLM request path 仍未通过”。
