# 05J_RK3588_正式执行流程

## 适用范围

本流程用于 RK3588 8GB 执行项目五 smoke、required 和 target run。执行边界与 05B 一致：项目三负责生成 RKNN detector raw，项目五负责 detector adapter、event package、文本解释、VLM/视频降级、Alarm JSON、per-event benchmark 和 stability raw。

本流程默认生成 post-detector chain、真实 RKLLM single-shot smoke 和真实 Qwen3-VL ROI single-shot smoke 证据。`20260710_rk3588_8gb_alarm_service_resident_detector_smoke_v2` 已经补齐了 RK3588 Project5 resident detector 10 分钟 smoke，`20260710_rk3588_8gb_alarm_service_resident_text_smoke_v1` 又补齐了 Project5 本地 resident text worker 的一次加载多请求复用证据，`20260710_rk3588_8gb_alarm_service_asset_worker_smoke_v1` / `v2` 则补齐了 Project5 本地 AssetWorker 的板端视频回放 smoke。当前源码还进一步补入了 detector-side `frame_cache_dir`：Project5 本地 detector 可以按 `frame_id` 写 bounded JPEG ring，供 service 在 camera/RTSP 场景回填同源帧资产；`20260711_rk3588_8gb_alarm_service_camera_frame_cache_smoke_v1` 已经补齐了第一条带真实事件的 camera frame-cache 资产 smoke。与此同时，`20260711_rk3588_8gb_alarm_service_resident_vlm_smoke_v1` 也已补齐 Project5 本地 resident VLM worker 的板端 smoke：`vlm_rows=3`、`vlm_bad_rows=0`，同一 `resident_server_pid=2436647`，`resident_model_load_count=1`，请求序号 `1/2/3` 递增，event/alarm/per-event/stability 四类 schema 全部 pass。更进一步，RK3588 已用收敛参数 `FRAME_CACHE_CAPACITY=512`、`SERVICE_QUEUE_CAPACITY=32`、`DETECTOR_QUEUE_CAPACITY=16`、`CLEAN_FRAME_CACHE_ON_EXIT=1` 依次补齐单板 P7/P8/P9：`20260713_rk3588_8gb_alarm_service_resident_concurrency_smoke_v3` 完成 10 分钟窗口，`20260713_rk3588_8gb_alarm_service_resident_required_v2` 完成 30 分钟 required，`20260713_rk3588_8gb_alarm_service_resident_target_v2` 完成 2 小时 target。它们已经不再只是“能跑通”，而是最新有效的 RK3588 单板常驻 service 证据。若要声明 RK3588 在线系统完成，必须继续执行 `projects/05_alarm_system/specs/05K_常驻服务与并发验收规范.md` 和 `projects/05_alarm_system/specs/05L_项目五独立代码库与适配边界规范.md`，证明 RKNN DetectorService、事件队列、RKLLM/Qwen3-VL worker 和 AlarmSink 在更长持续运行窗口内协同工作，且最终运行入口不直接耦合项目三/四脚本。

## 5B. 真实 RKLLM 文本解释

真实 RKLLM 使用项目五本地 adapter 调用 `rkllm_single_turn` runner。runner 二进制可以来自前序构建产物，但正式执行时建议复制或构建到 `projects/05_alarm_system/runners/`，并记录 hash。执行前必须确认 `.rkllm` 模型和 runner 存在：

```bash
export RKLLM_MODEL=models/llm_vlm/Qwen3-1.7B-RKLLM/qwen3_1_7b.rkllm
test -s "${RKLLM_MODEL}"
export RKLLM_TEXT_RUNNER=projects/05_alarm_system/runners/rkllm_single_turn/build/rkllm_single_turn
test -x "${RKLLM_TEXT_RUNNER}" || test -x ./rkllm_single_turn
```

建议先低频 smoke，不覆盖 template required run：

```bash
python3 projects/05_alarm_system/scripts/run_demo/run_llm_explain.py \
  --events benchmark/raw/05_alarm_system/${BOARD}/events/${RUN_ID}_events.jsonl \
  --model-config projects/05_alarm_system/configs/models/rk3588_model_combo.yaml \
  --mode rkllm \
  --model-path "${RKLLM_MODEL}" \
  --rkllm-wrapper projects/05_alarm_system/scripts/service/runtime_adapters/run_rkllm_single_turn.sh \
  --rkllm-runner "${RKLLM_TEXT_RUNNER}" \
  --ctx 2048 \
  --max-tokens 128 \
  --timeout-ms 60000 \
  --max-events 3 \
  --metrics-dir logs/runtime/05_alarm_system/${BOARD}/${RUN_ID}_rkllm_metrics \
  --output benchmark/raw/05_alarm_system/${BOARD}/${RUN_ID}_llm_outputs.jsonl \
  2>&1 | tee logs/runtime/05_alarm_system/${BOARD}/${RUN_ID}_llm_explain.log
```

真实 RKLLM pass 条件：

- 输入来自 event package。
- 输出包含 `event_id`、`status`、`mode=rkllm`、`llm_explanation`、`llm_raw_output`、`total_ms`、`metrics_json_path`。
- runtime log 和 monitor log 可追溯。
- bad rows 为 0，且 `llm_explanation` 不含 `I rkllm:`、`rkllm-runtime version`、`loading rkllm model` 等 runtime banner 后才继续 Alarm JSON。

若 `mode=template_fallback_interface_wiring` 或 `status=stub`，只能写成 template interface，不算真实 RKLLM。

## 5D. Project5 本地 AssetWorker 准备与 smoke

这一节记录的是 RK3588 已完成的第一阶段资产链路 smoke。目标不是继续复用离线抽帧脚本，而是在 `run_alarm_service.py` 内直接补齐 `keyframe_path`、`roi_paths` 和 `roi_crop_latency_ms`，为后续 resident/warm VLM 做准备。

当前 AssetWorker 边界：

- 只支持显式真实路径。
- 已支持 `video_file`、`video_playlist` 和 detector-side `frame_cache_dir`。
- 不支持直接从 live camera、OpenNI、RTSP 做 Python 侧 retro-seek；这类 live-source 必须通过 detector-side frame cache 提供同源帧。
- 对循环 playlist，必须显式打开 `--asset-playlist-loop`。

因此，这一步虽然属于项目五在线 service 内的资产回填验证，但它刻意不是摄像头实验。原因很直接：最初 `AssetWorker` 还没有 live-source 历史帧缓存或 ring buffer，无法仅凭旧事件 `frame_id` 回取摄像头过去某一帧；而 `video_file`/`video_playlist` 可以稳定 seek，所以先用它完成最小正确性验证。当前源码已补入 detector-side `frame_cache_dir`，下一步应基于它验证 live-source 资产链路。

建议先复用已经通过 RK3588 resident detector smoke 生成的 Project5 event package 做板端 smoke：

```bash

export BOARD=rk3588_8gb
export ENV_BASELINE_ID=20260611_rk3588_8gb_env_baseline

python3 projects/05_alarm_system/scripts/service/run_alarm_service.py \
  --run-id "${RUN_ID}" \
  --board "${BOARD}" \
  --environment-baseline-id "${ENV_BASELINE_ID}" \
```

## 5E. Project5 本地 camera/RTSP frame-cache 资产链路

### 6F.1 本次 10 分钟实验的目标、实现与边界

本节对应 `projects/05_alarm_system/specs/05M_常驻告警系统实施路线图.md` 的 P3。P3 通过后仍必须依次完成 P5 服务内 ROI 资产、P6 常驻 RKLLM/Qwen3-VL worker、P7 10 分钟全链路并发和 P8 30 分钟 required；本节不能替代后续阶段。

本实验验证的是 `resident_detector_smoke_pass_with_template_stub_workers`，不是最终 resident LLM/VLM 验收。执行时，Project5 service 只启动一次 detector 子进程；该进程启动时为每个 `inference_workers` 初始化并 warmup 一个 RKNN backend，运行窗口内持续复用。service 在 detector 仍运行时 tail 新增 JSONL，按规则把事件写入有界队列；独立 alarm worker 消费队列并持续生成 Alarm JSON。

`--text-mode template --text-max-calls 0` 和 `--vlm-mode stub --vlm-max-calls 0` 是刻意设置：它们不启动真实 LLM/VLM runner，因而 `llm_call_count=0`、`vlm_call_count=0`。这样可以单独证明 detector 常驻、规则触发、队列背压、AlarmSink、监控和 schema，而不会把单次模型冷启动时间混入 detector 稳定性结论。

本阶段的可靠性措施包括：detector JSONL 创建超时即失败；非零退出码即失败；tail 每 0.2 秒读取新增行；事件队列采用非阻塞 `put_nowait`，满时按 `drop_newest` 计数而不阻塞 detector；结束时 service 会停止 detector、等待 worker 结束并关闭 JSONL writer。真正的 LLM/VLM 常驻、故障自动重启和 worker 超时 fallback 是后续阶段，不能由本实验宣称。

### 6F.2 前台调试与 SSH 独立运行

P3 现在明确区分两种执行方式：

| 模式 | 命令 | 用途 |
|---|---|---|
| 前台阻塞 | `p05_rk3588_p3_control.py run` | 首次调试、定位启动即失败、要求错误直接显示在当前窗口 |
| 后台 detached | `p05_rk3588_p3_control.py start` | 已知链路可运行后，做 SSH 独立长时间窗口 |

前台阻塞模式允许直接在当前 SSH 窗口里跑完整 600 秒；如果 detector、service、schema 或预检查失败，错误会直接打印到当前窗口。后台 detached 模式仍然保留，用于避免 SSH 断开时丢失长跑窗口。tmux 不是运行依赖。

```bash

# SSH 断开后，以同一 control 的 status 命令检查状态。
```

第二个 SSH 会话可观察：

```bash

tail -F "${MONITOR_LOG}"
```

若 SSH 仍断开，重连后先检查而不是重跑：

```bash

last -x | head -20
```

判定规则：`uptime` 很短或 `last -x` 显示新 reboot 表示板端重启；`dmesg` 中出现 `Out of memory`、`Killed process`、NPU/driver error 表示资源或驱动故障；service/detector PID 仍在则多为 SSH 或客户端链路断开；PID 已消失但没有 reboot 记录则前台 hangup 或 service 失败。除非 stability raw 同时满足时长、schema 和状态门槛，否则上述任一情况都不能判为 P3 pass。

## 2026-07-13 RK3588 优化增量

本轮优化不再重复证明 RK3588 能否跑通，而是收紧 Project5 本地常驻服务的资源占用与产物规模，避免后续 `P7/P8/P9` 继续生成大量无用 `frame_*.jpg`。

| 优先级 | 优化项 | 已落地实现 | 目的 |
|---|---|---|---|
| P1 | detector 延后到 worker 就绪后再启动 | `run_alarm_service.py` 新增 `--detector-start-order after_workers`，`run_rk3588_p7/p8/p9` 默认启用 | 不再让 detector 在 resident text/VLM 尚未 ready 时白白写出几十秒 frame-cache |
| P1 | 只为真实 VLM 预算内事件提前抽资产 | `run_alarm_service.py` 在 `vlm_real_calls_only` 下按队列顺序预留前 N 个真实 VLM 名额，并在入队前执行 `asset_worker.enrich()` | 解除“第二个事件要等第一个慢 VLM 返回，frame-cache 只能拼命放大”的约束 |
| P1 | 收紧 detector frame-cache 容量 | `run_rk3588_p7/p8/p9` 默认 `FRAME_CACHE_CAPACITY` 已由 `1536` 再下调到 `512` | 在不丢真实 VLM 资产的前提下降低磁盘写放大和目录膨胀 |
| P2 | 失败时也清理 frame-cache | 上述三个 wrapper 保留 `EXIT` 清理路径，`CLEAN_FRAME_CACHE_ON_EXIT=1` 时成功或失败都会删除 `*_frame_cache/` | 避免实验中途中断后残留数千张 JPEG |
| P3 | 暂不压缩 service/detector 队列 | `SERVICE_QUEUE_CAPACITY=32`、`DETECTOR_QUEUE_CAPACITY=16` 维持不变 | 当前 `drop_count=0`，先守住稳定性，再考虑进一步缩容 |

### 为什么这次可以从 1536 压到 512

`frame_cache_dir` 是供异步 VLM 回填同源帧的内部 ring，不会写入最终 alarm schema。  
旧实现里，asset 提取发生在单线程 worker 内部；如果第一个真实 VLM 请求很慢，第二个事件直到几十秒后才开始读缓存帧，这就逼着 `frame_cache_dir` 保留很大的窗口。  
现在两件事已经同时改变：

1. `run_rk3588_p7/p8/p9` 改为 `--detector-start-order after_workers`，不再让 detector 在 resident worker 启动阶段提前刷掉缓存窗口；
2. `run_alarm_service.py` 会在 `vlm_real_calls_only` 策略下，按队列顺序只对前 N 个真实 VLM 事件提前抽取 `keyframe_path/roi_paths`。

因此，第二个真实 VLM 事件不再需要等到第一个 VLM 请求结束后才去 frame-cache 找图，`512` 张缓存帧已经足够覆盖 detector 到入队前的短窗口。
