# 05M_常驻告警系统实施路线图

## 1. 用途与最终目标

本文件是项目五从“模块 smoke”逐步走到“双板在线常驻告警解释系统”的唯一实施路线。它回答四个问题：当前处于哪一阶段、下一阶段要改什么和跑什么、通过后能声明什么、未通过时退回到哪里排查。板级命令分别见 `05I_Jetson_正式执行流程.md` 和 `05J_RK3588_正式执行流程.md`；双板并行执行顺序见 `05N_双板联调执行流程.md`；常驻验收字段见 `05K_常驻服务与并发验收规范.md`。

最终完成不是“模型能跑一次”，而是 Jetson 8GB 与 RK3588 8GB 各自都具备下面的 Project5 本地服务：

```text
视频/摄像头
  -> 常驻 YOLO detector（服务生命周期内加载一次；允许多 inference context）
  -> EventTrigger + 有界 EventQueue
  -> 常驻或 warm TextWorker（进程启动加载一次，处理多个 event_id）
  -> 常驻或 warm VlmWorker（vision + decoder 启动加载一次，低频处理多个 ROI）
  -> AlarmSink（持续写 schema-safe Alarm JSON 和 benchmark raw）
  -> Monitor + Supervisor（资源、超时、重启、fallback 可追溯）
```

“一次加载、常驻”按服务生命周期定义，不等于设备永不重启。受控重启后可重新加载，但必须记录 `model_load_count`、`restart_count`、冷启动耗时、warm 请求时延和影响范围。每事件新建 runner 并加载模型永远只能是 single-shot smoke。

## 3. P3 与 P4：先验证常驻 detector，而不是模型能力

P3 与 P4 的目的相同，分别在 RK3588 和 Jetson 上执行。二者都必须使用 Project5 本地 C++ detector runner，禁止把 Project3 raw replay 作为主路径。

实现流程：

1. `run_alarm_service.py` 通过 `ResidentProcessDetectorService` 用 `Popen` 启动一次本地 detector。
2. detector 在进程启动时创建每个 inference worker 的 RKNN/TensorRT backend，并执行 warmup；同一进程内的后续帧复用这些 backend。
3. service 在 detector 仍运行时等待 JSONL 创建并 tail 新增 frame row；规则引擎用连续帧、冷却时间和最小帧间隔生成 event package。
4. detector 生产线程只执行非阻塞 `BoundedEventQueue.put_nowait`。队列满时记录 `drop_count` 和 `drop_policy=drop_newest`，而不是等待解释任务。
5. 独立 alarm worker 使用 `template` 和 `stub` 生成回退解释并持续写 event、LLM、VLM、alarm、per-event raw、stability raw 和 service log。
6. monitor 覆盖整个窗口；正常结束后 service 停止 detector、等待 worker、关闭 writer；detector 非零退出、JSONL 就绪超时或非法 JSON 都使本次 run 失败。

P3/P4 的关键配置必须是 `--text-mode template --text-max-calls 0 --vlm-mode stub --vlm-max-calls 0`。预期 `llm_call_count=0` 且 `vlm_call_count=0`，证明测试窗口没有启动真实 LLM/VLM runner。此阶段测的是 detector 常驻、规则、队列、AlarmSink 与资源稳定性，不测模型质量。10 分钟窗口必须由 detector `--duration-sec 600` 实际控制；service stability raw 中必须同时满足 `requested_window_sec=600`、实际 `window_sec>=600`、`window_requirement_met=true`，否则本阶段失败。

持续运行阶段默认不应依赖普通 SSH 前台会话或 tmux 来维持最终 required 窗口，但首次调试允许先用 Project5 本地 `p05_rk3588_p3_control.py run` 做前台阻塞执行，让启动错误直接显示在当前窗口。确认链路可运行后，再用 `start` 以 `start_new_session=True` 启动 `run_rk3588_p3_resident_detector_smoke.sh` 子进程并记录 PID/status，避免 SSH 断开影响长窗口。P7/P8 最终服务应进一步以 Project5 本地 supervisor/systemd unit 管理，而不是以人工终端会话维持。SSH 断线后应先依据 `uptime`、`last -x`、service/detector PID、service log、detector log、monitor log 和 `dmesg` 区分网络空闲超时、前台 hangup、OOM、驱动错误或板端重启；没有完整窗口证据时不得重用局部产物声明通过。

## 4. P5：把视觉资产纳入在线服务

VLM 不能只接收 bbox；必须读取真实 keyframe 或 ROI 图片。因此 P5 在 Project5 内实现 `AssetWorker`，只消费经过规则筛选的低频事件，不进入逐帧 detector 热路径。

当前已完成的 `20260710_rk3588_8gb_alarm_service_asset_worker_smoke_v1` / `v2` 是第一阶段资产验证，不是摄像头实验。它使用 `video_playlist` 作为可 seek 的真实媒体源，把已有 event package 回填为 `keyframe_path`/`roi_paths`。在这一步之后，Project5 已新增 detector-side `frame_cache_dir`：detector 可按 `frame_id` 写 bounded JPEG ring，service 则以 `asset_source_type=frame_cache_dir` 读取同源帧。`20260710_rk3588_8gb_alarm_service_camera_frame_cache_smoke_v1` 先证明了这条 live-source pipeline 可以启动并稳定运行，但窗口内 `event_count=0`；随后 `20260711_rk3588_8gb_alarm_service_camera_frame_cache_smoke_v1` 已补齐带真实事件的 camera/RTSP 资产链路板端 smoke，拿到 `event_rows=3` 和 `CAMERA_FRAME_CACHE_RESULT=camera_frame_cache_asset_smoke_pass`。该 run 的 `window_sec=21.501` 不是异常提前退出，而是 P5 wrapper 固定 `MAX_EVENTS=3` 的 smoke 行为，收满 3 个事件即结束。因此当前路线图中的 P5 已不再缺 camera frame-cache 资产路径证据，下一缺口转为 Jetson P4 和 P7 detector+resident text/VLM 并发窗口。

| 设计项 | 实现要求 | 稳定性目的 |
|---|---|---|
| 输入 | event package 的 `frame_id`、`detections`、`roi_boxes`、视频/摄像头来源 | 确保资产可追溯到 detector 事实 |
| 输出 | `keyframe_path`、`roi_paths`、可选 `video_clip_path` 和生成状态 | VLM 按 `event_id` 精确消费真实图像 |
| 限流 | 只接收 EventQueue 中被选中的低频事件；限制并发和磁盘容量 | 防止抽帧/编码抢占 detector CPU、磁盘或内存 |
| 失败策略 | 资产不可读、超时或裁剪失败时写 `asset_status` 与 fallback | 故障只降级该事件，不能停 detector |
| 清理 | 按 run_id 管理临时文件和保留策略 | 防止长时间服务耗尽存储 |

P5 通过条件是：服务内生成的资产可读、路径写回 event/alarm raw、失败可追溯；它不证明 VLM 质量，也不允许复用项目三/四运行脚本作为最终运行时依赖。

## 5. P6：实现真正的常驻 LLM/VLM worker

P6 的实现必须位于 `projects/05_alarm_system/`。推荐使用 Linux Unix domain socket + JSON Lines 本地协议，避免引入外部消息中间件和跨项目运行时耦合。每类模型各有一个长生命周期子进程：

```text
run_alarm_service supervisor
  -> p05_text_worker_server
       startup: load Qwen3/RKLLM or llama.cpp model once
       ready: report pid, model_load_count=1, model hash
       request: {request_id=event_id, prompt, deadline}
       response: {request_id, status, explanation, warm_latency_ms}
  -> p05_vlm_worker_server
       startup: load vision RKNN + decoder RKLLM once
       ready: report both model hashes and model_load_count=1
       request: {request_id=event_id, keyframe_path/roi_paths, prompt, deadline}
       response: {request_id, status, answer, warm_latency_ms}
```

P6 的强制要求：

- 服务启动时先等待 worker `ready`；未 ready 不接收真实模型请求。
- 每个请求以 `event_id` 作为 `request_id`；禁止把上一个事件的上下文混入下一个事件。
- worker 必须能处理多个请求而不重新 exec runner；至少两次连续请求应证明第二次为 warm 请求。
- service 对每个请求设置 deadline。超时、socket 断开、worker 非零退出时，只输出该事件 fallback，并写 `worker_error`、`restart_count` 和原因。
- detector 不等待 worker socket 响应。队列满、worker 慢或 VLM 暂不可用时，按策略 defer/drop/fallback，不得阻塞 detector。
- RK3588 VLM 与 detector 可能竞争 NPU。VLM 调度必须低优先级、限频，并以 detector FPS、p95 和 drop 的实测变化决定是否允许并发或必须延期执行；不能仅凭“进程常驻”就声称性能隔离。

P6 最小证据为：单个 worker 处理至少 3 个事件，`model_load_count=1`、请求数大于 1、warm latency 有记录、进程 pid 在请求之间不变、输出按 event_id 对齐。此阶段仍是 worker 验收，不是全链路稳定性验收。

RK3588 已具备一条满足上述口径的 resident text worker 实测：`20260710_rk3588_8gb_alarm_service_resident_text_smoke_v1` 使用 `--events-input` 隔离 detector，service log 记录 `text_worker_info mode=rkllm_resident`，3 条 LLM 输出均为 `mode=rkllm_resident_service_worker`，同一 `resident_server_pid=2046602`，`resident_model_load_count=1`，请求序号 `1/2/3` 递增。该结果只能声明 `resident_text_worker_smoke_pass`，不能替代 P7/P8。

与此同时，Project5 本地 resident VLM 路径也已经补齐到仓库内部：`src/vlm_client/rkllm_resident_vlm_server.cpp`、`scripts/service/rkllm_resident_vlm_client.py`、`scripts/build/build_rk3588_rkllm_vlm_runners.sh`、`scripts/service/run_rk3588_vlm_resident_smoke.sh` 和 `run_alarm_service.py --vlm-mode rkllm_multimodal_resident` 都已落地。`20260711_rk3588_8gb_alarm_service_resident_vlm_smoke_v1` 已补齐板端 smoke 证据：在同一 `resident_server_pid=2436647` 下处理 3 个带 `keyframe_path/roi_paths` 的事件，请求间 `resident_model_load_count=1`，`resident_request_index=1/2/3` 递增，event/alarm/per-event/stability 四类 schema 全部 pass。因此，P6-VLM 已经从“代码就位”升级到“resident VLM worker smoke 已过”。

P8 最终报告必须给出 detector-only 基线与“detector + 常驻 LLM/VLM”对照表。若 VLM 导致 detector FPS、p95 或 drop 无法接受，则该板只能记录低频降级或调度失败，不能以 schema pass 代替并发验收。

## 7. 每个阶段的记录规则

每次 run 均在 `projects/05_alarm_system/runs/<run_id>/run.md` 写明：所属阶段、启动命令、模型是否真实加载、`model_load_count`、输入源、窗口、队列策略、monitor 路径、四类 schema 结果、可声明结论和下一阶段阻塞项。

| 现象 | 说明 |
