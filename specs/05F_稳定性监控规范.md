# 05F_稳定性监控规范

## 适用范围

本规范用于执行项目五完整告警系统的稳定性与监控实验。

稳定性实验不是附加项。项目五必须证明系统在固定输入源上持续运行时，高频检测、低频解释、事件队列、资源占用和异常恢复都可解释。

稳定性结论分两层：post-detector chain stability 证明项目三 detector realtime run 之后，项目五后处理链路可以闭环；resident service stability 证明 DetectorService、事件队列、LLM/VLM worker 和 AlarmSink 在同一持续运行窗口内协同工作。最终在线系统验收必须满足 `projects/05_alarm_system/specs/05K_常驻服务与并发验收规范.md`。

## 执行原则

执行者可以替换监控工具、服务管理方式或异常注入方式，但不能降低证据要求：必须保留 sustained raw result、资源曲线、异常注入日志、恢复结果和 MLPerf-style Summary。

## 路径口径

| 类型 | 路径 |
|---|---|
| run 记录 | `projects/05_alarm_system/runs/<run_id>/run.md` |
| raw result | `benchmark/raw/05_alarm_system/<board>/stability/` |
| processed result | `benchmark/processed/05_alarm_system/` |
| benchmark 日志 | `logs/benchmark/05_alarm_system/<board>/` |
| runtime 日志 | `logs/runtime/05_alarm_system/<board>/` |
| monitor 日志 | `logs/monitor/05_alarm_system/<board>/` |
| failure 日志 | `logs/failures/05_alarm_system/<board>/` |
| 稳定性报告 | `projects/05_alarm_system/reports/stability_report.md` |
| 降级报告 | `projects/05_alarm_system/reports/failure_and_fallback.md` |

## 前置条件

- 至少一块板完成端到端链路。
- 已冻结项目五模型组合，并在 `projects/05_alarm_system/reports/board_matrix.md` 中引用项目四准入结论。
- 已准备固定输入源和事件触发样例。
- 已准备资源监控脚本；当前可复用项目三 `monitor_jetson_tegrastats.sh` 和 `monitor_rk3588_rknpu.sh`，并把输出保存到项目五 monitor 路径。
- 已准备异常注入方式。
- 已定义模型组合和事件规则。
- 环境基线必须对齐 `projects/05_alarm_system/specs/00_environment_baseline_template.md`。
- run 记录必须对齐 `projects/05_alarm_system/specs/00_run_record_template.md`。
- 稳定性 raw 必须符合 `benchmark/schemas/alarm_system_stability_schema.json`。
- per-event 告警 raw 必须符合 `benchmark/schemas/alarm_system_raw_schema.json`。

如果项目四准入结论缺失，本 spec 只能验证检测链路、规则模板告警或 mock 模型调用的稳定性，不能写成 LLM/VLM 完整链路稳定性通过。

## 测试等级

| 等级 | 时长 | 用途 | 是否必做 |
|---|---:|---|---|
| smoke | 10 分钟 | 验证链路启动、事件包、JSON 输出 | 必做 |
| required | 30 分钟 | 项目五最低稳定性门槛 | 必做 |
| target | 2 小时 | 作品集验收目标 | 目标 |
| stress | 8 小时 | 生产化展示 | 可选 |

| 结论等级 | 含义 | 是否最终系统验收 |
|---|---|---|
| `schema_pass_not_stability` | event/alarm/raw schema 通过，但无持续窗口 | 否 |
| `post_detector_chain_pass` | detector 已实时运行，项目五后处理完成 | 否，只能说明链路闭环 |
| `single_shot_model_smoke` | 真实 LLM/VLM 对少量事件可执行 | 否，只能说明模型可调用 |
| `resident_service_smoke` | 常驻服务 10 分钟 smoke | 部分 |
| `resident_service_required` | 常驻服务 30 分钟 required | 是，最低最终验收 |
| `resident_service_target` | 常驻服务 2 小时 target | 是，作品集目标 |

## 执行步骤

### 1. 建立稳定性 run

新建：

```text
projects/05_alarm_system/runs/<date>_<board>_alarm_system_stability_<duration>/run.md
```

记录：

- board。
- environment_baseline_id。
- model_combo_id。
- 输入源。
- 事件规则。
- 队列容量和丢弃策略。
- LLM/VLM 超时。
- 监控工具和采样间隔。
- 异常注入计划。

### 2. 启动资源监控

当前仓库尚未提供 `projects/05_alarm_system/scripts/monitor/collect_system_metrics.py`。正式实现该统一采集器前，不允许直接引用该路径作为已执行命令；可用下面的板卡原生监控入口作为项目五稳定性监控证据。

Jetson：

```bash
RUN_ID=<run_id>
OUTPUT=logs/monitor/05_alarm_system/jetson_8gb/${RUN_ID}_tegrastats.log \
INTERVAL_MS=1000 \
bash projects/03_video_pipeline/scripts/monitor/monitor_jetson_tegrastats.sh &
echo $! > logs/monitor/05_alarm_system/jetson_8gb/${RUN_ID}_monitor.pid
```

RK3588：

```bash
RUN_ID=<run_id>
INTERVAL_SEC=1 \
bash projects/03_video_pipeline/scripts/monitor/monitor_rk3588_rknpu.sh \
  logs/monitor/05_alarm_system/rk3588_8gb/${RUN_ID}_rknpu_monitor.log &
echo $! > logs/monitor/05_alarm_system/rk3588_8gb/${RUN_ID}_monitor.pid
```

sustained 测试结束后必须停止监控：

```bash
kill "$(cat logs/monitor/05_alarm_system/<board>/${RUN_ID}_monitor.pid)"
```

如果监控脚本必须前台阻塞运行，run 记录必须说明它如何与 sustained 测试并行执行，并保存等价 PID、进程组或服务停止证据。若后续实现项目五统一 `collect_system_metrics.py`，必须保持输出字段能映射到本节 raw result 要求。

监控至少包含：

- CPU/GPU/NPU 利用率或替代证据；BPU 仅允许作为历史非主线证据引用，不能作为项目五正式板卡指标。
- 内存峰值。
- swap used。
- 温度。
- 功耗或电源模式。
- 进程存活状态。
- 队列长度。

### 3. 运行 sustained 测试

推荐命令：

当前仓库尚未提供 `projects/05_alarm_system/scripts/benchmark/run_stability_test.py`，下面是目标实现接口，不是当前可直接执行的命令。正式脚本完成前，必须按 05A/05B/05I 的端到端链路在固定输入源上持续运行，并保存 event package、alarm JSON、per-event raw、runtime log 和 monitor log；缺任一核心证据时不能写 `pass`。

```bash
python3 projects/05_alarm_system/scripts/benchmark/run_stability_test.py \
  --board <board> \
  --duration-min <10|30|120> \
  --source <fixed_video_or_camera> \
  --board-config projects/05_alarm_system/configs/boards/<board>.yaml \
  --output benchmark/raw/05_alarm_system/<board>/stability/<date>_<board>_stability.jsonl \
  > logs/benchmark/05_alarm_system/<board>/<date>_<board>_stability.log 2>&1
```

raw result 必须按时间记录：

```text
timestamp
detection_fps
event_count
event_count_by_alarm_domain
event_count_by_alarm_type
alarm_count
vlm_call_count
llm_call_count
event_queue_depth
drop_count
end_to_end_alarm_ms
memory_mb
swap_used_mb
temperature_c
power_w
fallback_count
fallback_count_by_alarm_domain
error_count
service_status
```

raw result 必须额外包含 `schema_version`、`measurement_granularity=time_window`、`target`、`model_combo_id`、`input_source_id`、`stability_tier`、日志路径和 `related_troubleshooting_id`，字段以 `benchmark/schemas/alarm_system_stability_schema.json` 为准。

### 4. 异常注入

至少覆盖：

| 异常 | 观测项 | 合格行为 |
|---|---|---|
| 摄像头/视频源断流 | 断流检测、重连时间、丢帧数 | 自动重连或进入 degraded 状态 |
| 事件突增 | 队列长度、drop count、告警延迟 | 队列有界，检测不被阻塞 |
| VLM 超时 | fallback_status、检测 FPS | VLM 超时不影响检测 |
| LLM 超时 | 模板告警、JSON 合格率 | 输出 schema-safe fallback |
| JSON 非法 | schema 修复次数、失败样例 | 保留原始输出和修复输出 |
| 内存压力 | memory、swap、OOM | 降级或退出可解释 |
| 温度升高 | temperature、FPS、tokens/s | 降频有记录，必要时限频模型调用 |

异常注入日志保存到 `logs/failures/05_alarm_system/<board>/`。

### 5. 聚合稳定性报告

当前仓库尚未提供 `projects/05_alarm_system/scripts/report/aggregate_stability.py`，下面是目标实现接口。正式实现前，可以手工或用一次性脚本聚合，但 run 记录必须保存聚合方法、输入文件、输出文件和校验结果。

```bash
python3 projects/05_alarm_system/scripts/report/aggregate_stability.py \
  --input benchmark/raw/05_alarm_system/<board>/stability/ \
  --monitor logs/monitor/05_alarm_system/<board>/ \
  --output benchmark/processed/05_alarm_system/<date>_<board>_stability_summary.csv
```

## 记录要求

- monitor 日志保存到 `logs/monitor/05_alarm_system/<board>/`。
- 失败日志保存到 `logs/failures/05_alarm_system/<board>/`。
- raw result 保存到 `benchmark/raw/05_alarm_system/<board>/stability/`。
- 报告写入 `projects/05_alarm_system/reports/stability_report.md`。

## 验收标准

- 高频检测和低频解释链路解耦。
- 10 分钟 smoke 必须通过。
- 30 分钟 sustained 必须通过，作为项目五最低门槛；未完成时状态只能是 `fail`、`blocked`、`not_verified` 或 `not_executed`，不能写成最终系统 `pass`。
- 如果 30 分钟 run 只是 Project3 detector realtime 加 Project5 后处理，状态必须写 `post_detector_chain_pass`，不能写 `resident_service_required`。
- 2 小时 sustained 作为作品集验收目标；未完成时必须说明原因和下一步，不影响 30 分钟 required 结论。
- 异常有恢复或明确降级。
- 报告包含 MLPerf-style Summary。
- 资源、温度、swap、功耗或电源模式完整。

## 降级和问题库

下面问题必须进入 `projects/05_alarm_system/reports/troubleshooting.md`：

- 内存不足、swap 过高。
- 温控降频导致 FPS 或 tokens/s 明显下降。
- VLM/LLM 阻塞检测链路。
- 事件队列持续堆积。
- 摄像头断流无法恢复。
- 异常注入后服务无法输出 schema-safe 告警。
