# 05N_双板联调执行流程

## 适用范围

本流程用于 Project 05 当前阶段的双板联调：

1. 双板 `30 分钟 required`
2. 双板 `2 小时 target`

它不替代单板规范。单板 accepted 路线、参数和板端产物仍分别以：

- `projects/05_alarm_system/specs/05I_Jetson_正式执行流程.md`
- `projects/05_alarm_system/specs/05J_RK3588_正式执行流程.md`

为准。本文件只定义“双板一起跑”时的组装口径、启动顺序、命名规则和联调通过标准。

## 当前双板 accepted 组合

当前双板联调不再追求“完全相同拓扑”，而是要求两块板都沿各自已经被证据证明可行的 accepted 路线运行：

| 板卡 | 当前 accepted 路线 | 正式入口 |
|---|---|---|
| Jetson 8GB | `resident detector + resident text + postrun async VLM enrichment` | `projects/05_alarm_system/scripts/service/run_jetson_p8_route_b_postrun_required.sh` / `run_jetson_p9_route_b_postrun_target.sh` |
| RK3588 8GB | `resident detector + resident text + resident VLM` | `projects/05_alarm_system/scripts/service/run_rk3588_p8_resident_service_required.sh` / `run_rk3588_p9_resident_service_target.sh` |

这不是偷换概念，而是当前工程事实：

- Jetson 已证明 `Route B postrun` 是 accepted 正式主线；
- RK3588 已证明同窗 `resident detector + resident text + resident VLM` 可长期稳定运行；
- 双板联调的目标是验证“两个正式单板方案同时成立”，不是强迫 Jetson 回退到已经被判定仅保留诊断意义的旧同窗 VLM 路线。

## 双板命名规则

双板 run 必须共享一个 `GROUP_RUN_ID`，然后派生各自板端 `RUN_ID`：

```bash
export GROUP_RUN_ID=20260716_p05_dual_board_required_v1
export JETSON_RUN_ID=${GROUP_RUN_ID}_jetson
export RK_RUN_ID=${GROUP_RUN_ID}_rk3588
```

双板 target 同理：

```bash
export GROUP_RUN_ID=20260716_p05_dual_board_target_v1
export JETSON_RUN_ID=${GROUP_RUN_ID}_jetson
export RK_RUN_ID=${GROUP_RUN_ID}_rk3588
```

最终报告中必须同时保留：

- `GROUP_RUN_ID`
- `JETSON_RUN_ID`
- `RK_RUN_ID`
- 两块板各自的 monitor/runtime/raw/schema 路径

## 双板 30 分钟 required

### 口径

双板 `required` 的通过条件不是“先后各跑一轮 30 分钟”，而是：

1. 两块板都各自满足单板 `resident_service_required`
2. 使用同一类输入场景和同一轮联调批次
3. 两块板的有效窗口必须**实质重叠**

当前双板 required 的组级通过标准定义为：

| 项 | 要求 |
|---|---|
| 单板 Jetson | `window_requirement_met=true`，`requested_window_sec=1800`，`drop_count=0`，Jetson accepted 路线产物完整 |
| 单板 RK3588 | `window_requirement_met=true`，`requested_window_sec=1800`，`drop_count=0`，resident text/VLM 同 pid / `model_load_count=1` |
| 启动偏差 | 两板 `run start` 的 UTC 时间差不超过 `300s` |
| 窗口重叠 | 两板有效窗口重叠时长不少于 `1500s` |
| 输入一致性 | 同一输入家族：都使用 `video_set_runtime_v1`，或都使用明确记录的 camera/RTSP 联调源 |
| 报告 | 两板各自四类 schema pass，并补一份组级 summary |

### 推荐启动顺序

1. 先在 Jetson 终端准备环境但不立即回车
2. 再在 RK3588 终端准备环境但不立即回车
3. 先启动 **Jetson**
4. 在 `60s` 内启动 **RK3588**

原因：

- Jetson accepted 路线含 `postrun async VLM enrichment`，收尾阶段比 RK3588 更长；
- 先起 Jetson 可以把窗口重叠风险压低；
- RK3588 已证明长期稳定，不需要作为联调节奏的主锚点。

## 联调后必须补的组级记录

双板联调结束后，不能只保留两块板的板端 stdout。必须额外补一份组级记录，至少包含：

| 字段 | 内容 |
|---|---|
| `group_run_id` | 双板联调批次 ID |
| `jetson_run_id` | Jetson 对应 run |
| `rk3588_run_id` | RK3588 对应 run |
| `tier` | `required` 或 `target` |
| `input_source_id` | 两板共同输入家族 |
| `jetson_start_utc` / `jetson_end_utc` | Jetson 有效窗口 |
| `rk_start_utc` / `rk_end_utc` | RK3588 有效窗口 |
| `start_skew_sec` | 启动偏差 |
| `window_overlap_sec` | 有效窗口重叠时长 |
| `jetson_status` / `rk_status` | 两板各自最终状态 |
| `aggregate_status` | `dual_board_required_ready` / `dual_board_target_ready` / `degraded` / `failed` |

当前仓库已补齐自动汇总脚本：

```bash
python3 projects/05_alarm_system/scripts/benchmark/summarize_dual_board_window.py \
  --group-run-id "${GROUP_RUN_ID}" \
  --tier target \
  --jetson-run-id "${JETSON_RUN_ID}" \
  --rk3588-run-id "${RK_RUN_ID}" \
  --jetson-stability benchmark/raw/05_alarm_system/jetson_8gb/${JETSON_RUN_ID}_alarm_system_stability.jsonl \
  --rk3588-stability benchmark/raw/05_alarm_system/rk3588_8gb/${RK_RUN_ID}_alarm_system_stability.jsonl \
  --output-json benchmark/processed/05_alarm_system/${GROUP_RUN_ID}_dual_board_summary.json \
  --output-md benchmark/processed/05_alarm_system/${GROUP_RUN_ID}_dual_board_summary.md
```

`required` 轮次只需要把 `--tier target` 改成 `--tier required`。
